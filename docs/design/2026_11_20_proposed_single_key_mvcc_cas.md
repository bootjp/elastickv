# Single-key compare-and-swap by MVCC commit timestamp

Status: Implemented behind a disabled-by-default feature flag. Three-host performance evaluation pending.

Author: bootjp

Date: 2026-11-20

## Decision

Add opt-in version metadata to `TransactionalKV.Get` and a dedicated `TransactionalKV.CompareAndSwap` RPC. A client that has read a live key can replace it if that exact version is still current. A client that receives the new version in a successful write response can use it for its next edit. The data group executes the comparison and replacement through its existing single-shard one-phase commit (1PC) path.

The expected saving is a read round trip when the caller already has the version and replacement. Existing single-shard 1PC already takes one data-group proposal on a successful, unbatched attempt. CAS also takes one. The case for adoption depends on which reads disappear and how much failed contention costs.

## What TiKV does

TiKV provides two relevant operations. Its transactional `Get` accepts a snapshot version and a `need_commit_ts` flag. The returned `commit_ts` identifies the write that produced the visible value. Its separate `RawCAS` compares the current bytes with supplied bytes, or tests for absence. The response reports success and the previous value or absence. The request also has column-family, TTL and delete fields. TiKV exposes per-key MVCC history to operators through `tikv-ctl mvcc`. ElasticKV can follow that diagnostic pattern independently of the point-read API. [TiKV protocol](https://github.com/pingcap/kvproto/blob/master/proto/kvrpcpb.proto) · [TiKV Control guide](https://docs.pingcap.com/tidb/stable/tikv-control/)

ElasticKV could implement the TiKV value predicate at the same atomic storage boundary. The choice is about the guarantee the caller needs. Suppose a client reads `A@10`, and two intervening commits write `B@11` and `A@12`.

| Requested update | Outcome against `A@12` | Appropriate use |
| --- | --- | --- |
| Replace if the bytes equal `A` | Succeeds | The current content is the entire precondition. |
| Replace if the version equals `10` | Returns a mismatch | The caller's decision is valid only while its observed revision is current. |

Value CAS also supports callers that know the expected bytes without ever reading a version. Version CAS avoids transmitting those bytes on each attempt and distinguishes intervening writes of identical content. Both require an atomic check. A future TiKV-compatible RawKV operation would need its own contract for absence, previous-value disclosure, TTL, deletion and keyspace mapping. TiKV's Go RawKV client also requires callers to coordinate atomic mode across writers to a key. ElasticKV must exercise ordinary writes, deletes and CAS against the same concurrency boundary. [TiKV RawKV client](https://github.com/tikv/client-go/blob/master/rawkv/rawkv.go)

## Public contract

| Operation | Request | Successful RPC response |
| --- | --- | --- |
| `TransactionalKV.Get` | Existing key and additive `need_commit_ts`, default false | An opted-in read returns the existing value and exactly one version result: a positive `commit_ts` for a live value, or an explicit `missing` marker. |
| `TransactionalKV.CompareAndSwap` | One public key, positive `expected_commit_ts`, replacement bytes (possibly empty) | One of `applied(new_commit_ts)` or `mismatch`. The applied timestamp is the actual new version. |

Use a protobuf `oneof` for each result so that an old Get server which ignores the request flag produces a distinguishable *absent result*. An opted-in client treats that response as unsupported. A supported server returns the live version even for a zero-length value. The read snapshot selects the visible record. Its timestamp, the Raft read index, and the key's last write timestamp have different meanings. For example, a read at snapshot 50 can return `A@10`. Only 10 is a valid token for that observation. The initial API uses the existing latest transactional read. History enumeration and arithmetic updates are outside this change. [Current public schema](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/proto/service.proto#L13) · [Transactional Get](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/adapter/grpc.go#L836) · [Read snapshots](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/kv/read_request.go#L143)

A mismatch is a normal, definitive outcome for this attempt. Missing, deleted, expired and differently versioned keys all mismatch. Zero is an invalid expected version. Replacing a live value preserves its absolute expiry and generates a fresh version even when the bytes are identical. The initial response omits the losing value. A caller that derives its replacement from current content must re-read and recompute after a mismatch. A transport timeout after submission leaves the outcome unknown. Retrying the old token cannot apply a second replacement once the original landed, but a later mismatch cannot identify the winner of the first attempt. Expose that ambiguity to the caller and disable transparent retries after uncertain submission.

The standalone RPC covers a decision based solely on the target key. A decision that also reads other keys retains its transaction snapshot and validates the complete OCC read set, including reads of absent point keys. Read dependencies outside the write shard use the existing multi-shard transaction. A range predicate additionally needs protection against insertions. Test write skew with two keys initially on: each client reads both and disables a different one conditional on the other. Independent single-key CAS operations may both succeed. Transactions validating both keys must admit at most one.

Only the exact key predicate can produce the dedicated mismatch verdict, including across leader forwarding. A store-wide commit timestamp fence can reject an unchanged target when an unrelated proposal arrives first. Keep that rejection, lock conflicts and routing failures distinct from a mismatch. Retry a proven non-effect only within the original deadline with the same expected version. Terminate the logical operation on an ambiguous submission.

## Read and apply paths

1. Carry an opted-in read through the existing snapshot, ownership and group fences, including remote reads. In memory, copy the bytes and timestamp from the same visible record under the read lock. In Pebble, decode the timestamp from the iterator key that produced the authenticated visible value. Preserve decryption, expiry and tombstone checks. If the read traverses a cache or a forwarding hop, propagate the complete result or report that version metadata is unavailable. A second latest-version lookup can pair an old value with a newer token. [Shard reads](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/kv/shard_store.go#L293) · [Memory store](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/store/mvcc_store.go#L342) · [Pebble store](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/store/lsm_store.go#L1192)
2. Validate the public key and route one replacement to its owning group. Add an explicitly gated exact-version predicate to the replicated 1PC mutation and carry it through forwarding and replay. The coordinator issues the new commit timestamp through the normal fenced leader path. The client token never supplies the new write time or the transaction start time. Keep existing lock, timestamp and migration admission checks. [Replicated mutation format](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/proto/internal.proto#L37) · [Single-shard dispatch](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/kv/sharded_coordinator.go#L1905)
3. At apply, inspect the latest logical record, including earlier staged writes in the same entry. Require its version to equal the expected timestamp, require it to be live at the replicated write timestamp, and require the new timestamp to advance it. Use the store's Raft-entry staging scope for the CAS request. Evaluate the predicate in that scope before recording migration progress. Stage the tracker update, replacement, preserved expiry and durable applied index in the same batch, and publish notifications after commit. On an operational failure discard the entire scope and halt apply. On a mismatch explicitly persist only Raft progress, including for an otherwise empty Pebble batch. Add a tracking-armed test which compares the tracker and user record before rejection, after rejection and after restart. A mismatch stages no user write, migration effect or notification. Applying a committed no-op still advances the applied index. Keep operational failures distinct from per-request verdicts. Check durable entry replay before evaluating the predicate again. [1PC apply](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/kv/fsm.go#L2260) · [Pebble entry staging](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/store/raft_entry.go#L307)
4. Verify that each visible logical overwrite gets a distinct, increasing version for its key, including through leader and ownership changes. Low-level historical writes can reuse a timestamp. Permit identical replay, and audit import, restore and migration paths for same-version replacement with different data before enabling CAS. Scope tokens to a key in one cluster history. A Raft snapshot install continues the same history. An administrative rewind can resurrect an old token. Require a new cluster incarnation bound to requests after a rewind, or keep CAS disabled on that restored cluster until old clients are fenced.

## Where operations are saved

The counts below model one logical attempt after feature activation, for a leader-connected client, one data group, no retries and one write per proposal. A client RPC is one application request/response. A data proposal is one call to the data-group Raft proposer. A quorum read fence, timestamp-service call, frontend-to-leader forward and Raft replication message each have their own counter. The baseline at `6943eff8a` sends one 1PC request to `Txn.Commit`; the proposal path serializes the requests and calls `Propose`. The public `PreWrite` and `Commit` handlers at that revision are stubs. The baseline below uses working internal 1PC, behind a benchmark-only frontend where necessary. [Single-shard commit](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/kv/sharded_coordinator.go#L2156) · [Proposal boundary](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/kv/transaction.go#L153) · [gRPC handlers](https://github.com/bootjp/elastickv/blob/6943eff8ab66143ad023629dd238906eddd5a989/adapter/grpc.go#L800)

| Work performed inside the timed update | Existing 1PC baseline: client RPCs / data proposals | Version CAS: client RPCs / data proposals | Explanation |
| --- | ---: | ---: | --- |
| Caller holds a token and replacement. Baseline opens a fresh read and submits its validated write as two client calls. | 2 / 1 | 1 / 1 | CAS removes the fresh read. Account separately for the earlier read that produced the token. |
| Same input, with the baseline read, check and 1PC submission inside one server handler | 1 / 1 | 1 / 1 | CAS can remove the handler's pre-read, its value copy and any remote storage read. Both still check storage at apply. Count the actual storage probes and timestamp allocation path on both sides. |
| Caller retains its original validated snapshot and prepared value | 1 / 1 | 1 / 1 | Charge acquisition, pin time, expiry and release in a separate full-lifecycle cell. |
| Caller must read the current value to compute the replacement | 2 / 1 | 2 / 1 | Both need the read. On conflict, recomputing requires a fresh read. |
| Supplied token is already stale when the server handles it | 1 / 0 with a fenced pre-read and early rejection | 1 / 1 with apply-only comparison | A failed CAS can consume **more** Raft work. A CAS variant with a linearizable precheck can reach 1 / 0 when it proves the mismatch. |
| Two callers observe the same version and both reach proposal before either update is applied | 2 write calls / 2 proposals across both callers | 2 write calls / 2 proposals across both callers | One winner in both designs. Initial reads are outside this row. |

Blind `Get` followed by unconditional `Put` allows a lost update. For the equivalent 1PC control, read the value and its version at one fenced snapshot, reject an unexpected version, and submit the replacement using that snapshot's start timestamp and the key in the OCC read/write set. The benchmark frontend owns the original read scope and gives the client a single-use handle bound to that key, snapshot and client. Release its pin on submission, cancellation or expiry (five seconds). Record expired handles and memory/pin time. The retained-handle arm acquires the handle alongside the original read. The two-call fresh-read arm acquires it during the timed update. The single-handler control performs the same work locally. Keep the original start timestamp through submission. Use only fenced 1PC writers and non-expiring keys in the equivalent-control trials. Verify the replicated timestamp fence on every participating node. A delayed raw write at 15 can replace the visible version at 5 after the baseline took snapshot 20 when the fence is inactive. OCC then accepts a version changed below its snapshot, while exact CAS rejects. Exercise that history separately with fence activation on and off. Require active protection across mixed raw and transactional writers before enabling the write RPC, and test identical timestamp rewrites, import, migration and TTL separately. If a fenced precheck rejects R stale attempts before submission, it can avoid R individual proposals relative to proposing all attempts. The same precheck on both designs offers no inherent proposal advantage to CAS. Compare its read cost with the proposals actually avoided.

## Contention benchmark

**Setup.** Use three Linux voters on separate hosts, one data group with a fixed leader, a separate load generator, TLS, synchronous persistence and identical server settings. Use the sharded coordinator, record the leader timestamp allocation mode, and hold it fixed across builds. Use clean keys without secondary locks. Test fresh-read two-call 1PC, single-handler fresh-read 1PC, retained-handle 1PC and apply-only CAS. A zero start timestamp can trigger an internal latest-version probe even when the public Get disappears. Repeat with follower ingress and a separate secondary-lock-resolution fixture before attributing remote reads or proposals to the optimization. Measure optional fenced precheck CAS as a separate variant. Use the same seeded keys, payloads, traces, deadlines and retry policy. Keep the common opt-in read helper in all benchmark builds. Record revisions and settings; the following are planned experiments.

| Workload | Parameters | What it tests |
| --- | --- | --- |
| Known token and read-dependent update | Uniform over 65,536 keys; 64 B, 1 KiB and 16 KiB values; 1, 8 and 32 workers | Separate saved reads from operations that intrinsically need a read. Run once with preloaded tokens and once charging their acquisition. |
| Synchronized contenders | Give 2, 8 or 32 writers the same token and distinct replacements. Release them together, disable retries and reset between rounds. Repeat at least 1,000 rounds per cell. | Count admissions, precheck passes, submitted proposals, applied predicate evaluations and definitive outcomes. Exclude setup and reset from every counter. In a second instrumented trial park all contenders after precheck and before proposal. Require one winner among valid monotonic timestamp attempts and attribute every loser to its actual reason; retry a certified timestamp-order rejection separately when testing the one-winner history. |
| Known stale tokens | Inject exactly 0%, 10%, 50%, 90% or 100% stale tokens on otherwise disjoint keys. Use each prepared key/token pair once in a window to keep the injected fractions exact. | Isolate early rejection from races after precheck. At 100% stale, report absolute proposals and cost per attempt. Cost per success is undefined. |
| Sustained contention | Uniform keys, 90% of requests on one key, and a single hot key. Drive identical open-loop arrivals at 50% and 80% of the baseline saturation rate. | Measure queueing, deadline misses and useful throughput. Run both single-attempt mode and a recompute loop capped at four attempts with identical seeded backoff and one end-to-end deadline. |

For sustained runs, warm up for 30 seconds and measure at least 120 seconds. Alternate build order over ten matched pairs. Count logical updates separately from attempts. Capture client RPCs by method, internal forwards, timestamp calls, ReadIndex operations, data proposals, committed entries, writes per entry, comparison reads, bytes sent, server CPU and allocations. Record injected staleness as an input label. Classify each attempt by the returned verdict so an injected-stale attempt rejected by the timestamp fence counts as a fence rejection. Publish applied updates/s, RPCs and data proposals per attempt **and per successful update**, and p50/p95/p99 from scheduled arrival through the final outcome. Report successes, mismatches, exhausted retries, unsent or timed-out requests and unknown outcomes separately. The pinned implementation submits transactional requests individually. Its raw batcher combines raw requests only. Distinguish commands per proposal, proposals per committed entry and entries per durable flush. Count internal RawGet, RawLatestCommitTS, Forward, ForwardCompareAndSwap and RaftAdmin.Status by method. Include membership lookup, capability probes and timestamp-service traffic in the end-to-end latency and internal RPC totals. Report first-use activation proposals and reads separately from steady state. Separate rerouting, timestamp rejections, exact mismatches, locks and unknown outcomes. Reconcile counters with the history of each successful change.

**Decision rule.** Correctness gates rollout. In the known-token two-call comparison, verify the predicted change from two client RPCs to one and one data proposal on both sides. Use the single-handler 1PC control for the performance decision. For the primary cell, use 1 KiB values, eight outstanding workers, leader ingress, known tokens prepared outside the measurement, and uniform disjoint per-worker key partitions. Update the cached version from each successful response in every arm (the fixture exposes the 1PC commit timestamp). Warm up the same way before each measurement. Replenish a rejected token only through a counted read. For the retained-handle arm count reacquisition when the handle is consumed. Also publish acquisition-inclusive results.

Calibrate using the single-handler 1PC control. Double the offered rate from 16 logical updates/s until a 120-second window achieves less than 99% on-time successes, then use bisection to within 5% of the highest passing rate. Run the primary and each hot-key cell at 80% of its own control's calibrated rate (50% is diagnostic), with a 1 s deadline measured from scheduled arrival, including queue time. If the worker cap delays dispatch, count queueing and every unsent request. Freeze rates, traces and seeds before candidate runs. Hot-key decision cell: one key, eight workers, 1 KiB, four total attempts, full jitter using the same seeded uniform distribution from zero to 1, 2 and 4 ms on successive retries. For contention calibration use completed logical outcomes within deadline as the 99% criterion, record control goodput and compare goodput at that fixed offered rate.

The primary metric is p99 among successful logical updates from scheduled arrival to confirmation. Record all-outcome latency separately. Compare ten matched candidate/control pairs using the median paired ratio and the interval from the second to ninth order statistic. Require primary upper p99 ratio ≤0.90, hot-key upper successful p99 ratio ≤1.05, and lower successful-throughput ratio ≥0.95 in both cells. Require zero unknown outcomes and at most 1% deadline misses or unsent requests combined in every arm of both decision cells. Require at least 1,000 successes per evaluated p99; if any cell falls short rerun both arms with the same longer window. Report inconclusive intervals and defer adoption. Compare retained handles independently and publish the workload share benefiting from the fresh-read comparison before extrapolating savings. ## Initial implementation scope

The first release targets ordinary byte-range keys on protected data groups. Production uses the sharded coordinator even for a single data group. The legacy coordinator lacks authoritative route history and rejects CAS before proposal. A forwarded CAS uses a dedicated internal RPC. A peer running an older binary rejects the method before it can append the operation in the legacy format. The new Raft frame also identifies the operation during replay.

Start an eligible protected runtime with `--commitTSFence` and `--versionCAS`. Before serving the first token or admitting the first CAS, the group must have applied the commit timestamp fence. The leader also proposes a durable marker requiring imports and promotion to preserve the bytes, expiry and deletion state of existing CAS-visible version heads. Concurrent first users share activation. Once active, a matching historical import is idempotent and a conflicting import is refused. An external snapshot rewind makes the restored runtime ineligible for CAS.

Versioned reads and CAS initially require an active range with ordinary byte-key routing and no migration ownership evidence or migration write floor. A range that moved away and back can still carry that evidence. The API returns a capability or routing error for these ranges. This restriction allows old groups to replay their historical migration commands while the first rollout protects the identity of every token it issues.

The proposal gate contacts the other configured voters and learners to check capability. For a three-voter group without learners, a live check can add two peer status RPCs per attempt, in parallel. Include these in the production benchmark. A local fixture that replaces this gate can establish public RPC and data-proposal counts, but cannot establish the three-host latency or adoption criteria. Report the cost of activating a newly eligible group separately.

The single-voter smoke run confirmed the predicted public RPC and data-proposal counts. Eight contenders for one version produced one successful update per round. The 100% stale case used one proposal per attempt for apply-only CAS and zero proposals for either fresh-read control. [Recorded contention counters](../evidence/2026_11_20_single_key_mvcc_cas_review.md#local-contention-counters-2026-11-21)

Ordinary reads and writes also need a performance comparison with the flag off. Three short, interleaved local samples showed unchanged allocation counts for ordinary 1PC and reads. Median times for adapter reads backed by Pebble and for 1PC increased, with overlapping ranges in all cells. Repeat on dedicated hosts before enabling the feature. [Ordinary-path measurements](../evidence/2026_11_20_single_key_mvcc_cas_review.md#ordinary-path-measurements)

## Delivery and verification

1. Implement opt-in transactional Get across memory, Pebble and forwarding. Verify missing and empty values, historical visibility in the underlying reader, expiry, encrypted values and old-server responses. Benchmark ordinary Get for regressions.
2. Add the dedicated RPC and gated replicated predicate. Enable proposal only when the group, including learners and forwarding paths, supports the command. An old frontend returns an unsupported-method error. Prevent incompatible membership changes or binary downgrade while the log may still contain this command. To disable new use, stop admission and drain accepted work.
3. Run model-based single-key histories with puts, deletes, reads and CAS. Cover identical-value rewrites, delete/recreate, TTL at the boundary, concurrent requests in one entry, routing changes, dropped replies, leader loss, WAL replay and snapshot restore. Verify one winner per observed version, durable successful acknowledgments, deterministic mismatch verdicts and absence of effects on rejected attempts.
4. Run the paired benchmarks and publish raw counters, latency distributions, histories and configuration alongside the decision. Decide separately whether a measured rate of stale submissions justifies adding the fenced precheck.
