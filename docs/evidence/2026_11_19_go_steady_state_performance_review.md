# 現行 Go 実装の平常時性能改善計画の独立レビュー

対象は[平常時の性能改善計画](../design/2026_11_19_proposed_go_steady_state_performance.md)（SHA-256 `629edb06ef082349825382664edbddd742a40057cf85b0b285ade33c8d5676e3`）。2026-11-19 に設計、基準コミットの実装、既存の診断ログを静的に照合した。

設計書の SHA256 は指定値と一致しました。実装の参照先はすべて `afe0a9f9d` です。Linux 診断の `before-read` と `before-write` はともにエラー 0 件でした。以下の4件は、現行 Go で観測した障害ではなく、提案どおりに実装・評価した場合の条件付きリスクです。

1. **P1 — FSM の集約単位と、途中失敗時に確定する範囲を明記する。** 設計書 43–45、66 行。現行 FSM は、1 個の Raft entry に含まれる複数の Raw 要求をすでに一括適用します。OCC 競合などの確定拒否は要求別に返し、store の読み出し・commit 失敗では entry 全体を破棄して `HaltApply` とし、適用通知も破棄します。異なる applied index を既存 batch に渡すと、先に積んだ更新も破棄されます。[kv/fsm.go:486](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/kv/fsm.go#L486)、[kv/fsm.go:505](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/kv/fsm.go#L505)、[kv/fsm.go:523](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/kv/fsm.go#L523)、[store/raft_entry_test.go:205](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/store/raft_entry_test.go#L205)。設計書の「要求の集約」だけでは、提案前に複数要求を一つの entry にする案と、commit 済みの複数 entry を一度に apply する案で、同じ失敗処理を使えてしまいます。**修正案**は、どちらを採るか明記することです。前者では同じキーに「成功・直前の更新と競合・成功」を並べ、要求別の結果、最終値、通知を逐次版と照合します。後者では連続3 entry の中央に適用障害を注入し、完了済みの先頭、失敗位置、未実行の末尾について、応答・通知・durable applied index・再起動後の値を照合します。既存の完了済み先頭を検査する例は [internal/raftengine/etcd/engine_storage_pipeline_failure_test.go:495](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/internal/raftengine/etcd/engine_storage_pipeline_failure_test.go#L495) にあります。

2. **P1 — WAL 保存をまとめる際に、永続化を待つ Raft の通知と進行条件を固定する。** 設計書 39–45 行。同期経路では `Ready` ごとに snapshot があれば先に保存し、entries が空でも `HardState` に更新があれば保存します。保存に失敗すると、その `Ready` の apply・dispatch・`Advance` に進みません。[internal/raftengine/etcd/wal_store.go:937](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/internal/raftengine/etcd/wal_store.go#L937)、[internal/raftengine/etcd/engine.go:2496](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/internal/raftengine/etcd/engine.go#L2496)。要求件数だけを集約の契機にすると、投票などユーザー write を伴わない更新が滞留し得ます。また、キューへの受理を保存完了として扱うと、必要な永続化より先に peer へ応答し得ます。成功 write の復旧検査だけでは、どちらも検出できません。**追加試験**では、write が来ない状態で `HardState` のみの `Ready` を処理し、次の要求を待たずに保存することを確認します。さらに `Save` と必要な `Sync` を個別に停止・失敗させ、該当する永続化に依存する応答が出ないこと、失敗位置を越えて進まないことを確認します。明示的な非同期経路には両故障を分ける試験があります。[internal/raftengine/etcd/engine_storage_pipeline_failure_test.go:283](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/internal/raftengine/etcd/engine_storage_pipeline_failure_test.go#L283)。

3. **P2 — 同じ測定結果から同じ採否を出せるよう、負荷と判定式を事前に固定する。** 設計書 53–65 行。現行の条件では、対象負荷で CPU が 10% 改善すれば、同じ負荷の p99 が大幅に悪化しても、63 行の「他の負荷」の上限には抵触しません。また、固定到着率の具体値、混合負荷の read/write 別の判定、5 組以上の結果をどう集約して「ばらつき」を判定するかが未定です。既存診断は write が 2.023 秒で成功 625 件であり、混合負荷でも read と write の p99 はそれぞれ 4.297 ms と 24.143 ms です。全要求をまとめるか操作別に見るかで結論が変わり得ます。`docs/evidence/performance_20261119/api_split_linux.txt:3`、同 `:4–5`。**修正案**は、基準測定後・候補測定前に、対象の負荷条件と主指標、到着率、同時実行上限に達した予定要求の扱い、ウォームアップ・測定時間、反復数を表に固定することです。例えば各組の候補／基準比から中央値と事前指定した信頼区間を算出し、主指標は区間上限が 0.90 以下、対象負荷を含む各操作の p99 は上限 1.05 以下、飽和 throughput は下限 0.95 以上を採用条件とします。成功率の許容差と結果不明率の上限も数値化し、区間が閾値をまたげば保留とします。

4. **P2 — `RawGet` のログ引数に帰属する費用は、値長を振る段階から対照実験で測る。** 設計書 27–30、54 行。成功経路で `InfoContext` の呼び出し前に key と value を文字列化する記述は確認できます。一方、Pebble の point read でも `decodeValue` が値長分を `make`・`copy` します。Warn で総 bytes/op が値長に比例しても、その傾きだけではログ引数の寄与を特定できません。[adapter/grpc.go:256](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/adapter/grpc.go#L256)、[store/lsm_store.go:1201](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/store/lsm_store.go#L1201)、[store/lsm_store.go:637](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/store/lsm_store.go#L637)。**修正文案**は「64 B、1 KiB、16 KiB の各値長で、同じ成功 hit 列・Warn 設定・読み取り経路を使い、現行版と `Enabled` ガードだけを加えた版を対にする。各値長の bytes/op と CPU/op の版間差をログ引数生成の効果として報告し、別実行の割り当てプロファイルで発生箇所を照合する」です。

**総合判定は要修正です。** 既存の `before-*` と単発 store ベンチを診断値に限定する判断は妥当ですが、書き込み集約の失敗境界と、読み取りの費用帰属・性能採否の判定手順を実装前に確定する必要があります。
