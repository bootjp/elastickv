# Independent review of the Go steady-state performance plan

**Verdict at review time (2026-11-19): revisions required.** The review compared the proposed design with the implementation at `afe0a9f9d` and the existing diagnostic logs. The reviewed document matched SHA-256 `629edb06ef082349825382664edbddd742a40057cf85b0b285ade33c8d5676e3`. Line numbers below refer to that revision. The Linux `before-read` and `before-write` phases both completed with zero errors. The findings describe risks in the proposed changes and evaluation. [Current steady-state performance design](../design/2026_11_19_proposed_go_steady_state_performance.md)

### P1. Define the unit of FSM batching and the failure boundary

Design lines 43–45 and 66. The FSM already applies the raw requests in a single Raft entry as a batch. It returns deterministic rejections such as OCC conflicts per request. A store read or commit failure discards the entire entry and its pending notifications and returns `HaltApply`. Passing a different applied index to an existing batch also discards its staged updates. [kv/fsm.go:486](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/kv/fsm.go#L486), [kv/fsm.go:505](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/kv/fsm.go#L505), [kv/fsm.go:523](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/kv/fsm.go#L523), and [store/raft_entry_test.go:205](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/store/raft_entry_test.go#L205)

Specify where batching takes place. If requests are combined before proposal, issue three writes to the same key so that the first succeeds, the second conflicts with it, and the third succeeds. Compare individual results, final value, and notifications with sequential execution. If the change batches the application of already committed entries, inject a failure in the middle of three consecutive entries. Check responses, notifications, the durable applied index, and values after restart for the completed first entry, the failed entry, and the unexecuted last entry. [Existing completed-prefix test](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/internal/raftengine/etcd/engine_storage_pipeline_failure_test.go#L495)

### P1. Specify which Raft actions wait for WAL persistence

Design lines 39–45. On the synchronous path, each `Ready` saves its snapshot first if present, then saves a changed `HardState` even when there are no entries. A save failure prevents apply, dispatch, and `Advance` for that `Ready`. A batch triggered only by user writes can leave a vote waiting indefinitely. Treating queue admission as a completed save can send a peer acknowledgment before the required data is durable. [internal/raftengine/etcd/wal_store.go:937](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/internal/raftengine/etcd/wal_store.go#L937) and [internal/raftengine/etcd/engine.go:2496](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/internal/raftengine/etcd/engine.go#L2496)

Recovering acknowledged user writes alone would miss both cases. Submit a `Ready` containing only a `HardState` update and verify that it is saved without waiting for another request. Block and fail `Save` and the required `Sync` separately. Verify that dependent responses wait and progress stops at the failure. The explicit asynchronous path already has tests that distinguish the two failures. [internal/raftengine/etcd/engine_storage_pipeline_failure_test.go:283](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/internal/raftengine/etcd/engine_storage_pipeline_failure_test.go#L283)

### P2. Fix the workload and decision rule before measuring the candidate

Design lines 53–65. A 10% CPU improvement on the target workload could satisfy the proposed rule even if its p99 regressed substantially. The p99 limit on line 63 only covered other workloads. The plan also left open the arrival rates, how to evaluate mixed reads and writes, and how to combine five or more paired runs. In the Linux diagnostic, the write-only run completed 625 writes in 2.023 seconds. Mixed-workload p99 was 4.297 ms for reads and 24.143 ms for writes. Pooling these samples could change the decision. See `api_split_linux.txt`, lines 3–5. [Linux measurements](2026_11_19_steady_state_linux_baseline.md)

After measuring the baseline and before testing the candidate, record the target configuration, primary metric, arrival rates, handling of requests queued at the concurrency limit, warm-up and measurement windows, and repetition count. One proposed rule uses the median paired candidate/baseline ratio and a prespecified confidence interval. Require an upper bound of 0.90 for the primary metric, an upper bound of 1.05 for each operation's p99 including the target workload, and a lower bound of 0.95 for throughput at saturation. Specify the success-rate tolerance and maximum unknown-outcome rate. Defer adoption when an interval crosses a threshold.

### P2. Isolate the cost of preparing RawGet log arguments

Design lines 27–30 and 54. On a hit, the baseline handler converts the key and value to strings before calling `InfoContext`. Pebble also allocates and copies the payload in `decodeValue`. Either operation can make allocated bytes per read grow with value size at Warn level. [adapter/grpc.go:256](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/adapter/grpc.go#L256), [store/lsm_store.go:1201](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/store/lsm_store.go#L1201), and [store/lsm_store.go:637](https://github.com/bootjp/elastickv/blob/afe0a9f9dc1542b4a039a6a0392776a41370e1ef/store/lsm_store.go#L637)

For each of 64 B, 1 KiB, and 16 KiB, run the same sequence of hits through the same read path at Warn level. Pair the baseline with a candidate that adds only the `Enabled` guard. Report the differences in bytes/op and CPU time/op at each size, then collect separate allocation profiles to identify the contributing call sites.

The early `before-*` runs and single-operation store benchmark are appropriate diagnostic evidence. Before implementation, the review called for specifying the write failure boundaries, isolating the read allocation cost, and defining the performance acceptance rule.
